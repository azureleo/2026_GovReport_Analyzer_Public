# 서울 시각요소 VLM 벤치마크 v1 — 한국 공공문서 차트 판독 성능 비교

> 작성: 2026-07-07. 상태: **v1 확정** (claude·openai만 조건 미충족으로 미측정).
> 한 줄 요약: 같은 문서·같은 정답지·같은 파이프라인에서 **vision 모델만 바꿔가며**
> "한국 지자체 보고서의 차트·도식을 구조화 데이터로 읽어내는 능력"을 측정했다.

## 1. 무엇을 측정했나

### 1.1 태스크

한국 지자체 탄소중립 기본계획 보고서(서울, 515쪽 PDF)에는 텍스트로 추출할 수 없는
정보가 시각 요소(그래프·도식·이미지)로만 존재한다. 벤치마크의 질문은 하나다:

> **vision 모델이 이 시각 요소들을 발견하고, 그 안의 데이터를 읽어내어,
> 파이프라인의 구조화 시트(`16_시각자료목록`)까지 도달시키는가?**

측정 단위는 "요소"다. 사람이 확정한 시각 요소 목록(정답지)의 각 요소에 대해,
파이프라인 출력에 그 요소의 판독 기록이 존재하면 성공(기록됨), 없으면 실패이며
실패는 어느 단계에서 죽었는지(아래 1.3)로 분류된다.

### 1.2 정답지 (ground truth)

`data/golden/서울_시각요소_인벤토리_v1.xlsx` — 제작 계보:

1. PDF 텍스트 레이어에서 `[그림 N-N]`/`[표 N-N]` 캡션 1,035건 수확 → 목차 중복 제거
   → 본문 고유 캡션 505건.
2. 텍스트 레이어가 살아 있는 표 324건 제외(그건 텍스트 추출 경로의 몫) → 시각요소
   후보 181건.
3. 3라운드 교정: ① Claude가 페이지를 직접 보며 96건 판독 분류, ② 사람이 "이미지표"
   전수 원문 확인(6건 전부 오분류로 판명 — 렌더 이미지만으로는 텍스트표와 구분
   불가한 계통 오류를 사람이 교정), ③ 유실 요소 재검토로 국가·전국 참고자료와
   방법론 도식 재분류.
4. 최종: 요소 176개, 그중 **기대추출=Y 82개**(그래프 77, 데이터 도식 5)가 리콜 분모.

핵심 설계 판단: "예쁜 그림"이 아니라 **파이프라인이 마땅히 읽어야 할 요소**만
분모에 넣었다. 장식·사진·국제 참고사례·정성 도식은 기대추출=N으로 분모에서 뺐고,
그 판단 근거는 인벤토리의 행별 비고에 남아 있다.

### 1.3 지표

| 지표 | 정의 |
|---|---|
| **리콜** (1차) | 기대추출 82요소 중 `16_시각자료목록`에 기록된 비율 |
| 유실 단계 | 실패를 파이프라인 깔때기 단계로 분류: 이미지_미추출 → triage_탈락 → 참고자료_제외 → **vision_유실**(이미지·triage는 통과했는데 모델이 데이터를 못 읽음) |
| 데이터포함률 (2차) | 기록된 항목 중 실제 수치를 담은 비율 |
| 표본 값정확도 (3차) | 모든 후보가 공통 기록한 요소 15개의 판독값을 나란히 놓고 원문과 대조(사람 판정) — `표본채점지.md` |

이 벤치마크에서 **모델 간 차이를 만드는 단계는 vision_유실뿐**이다 — 이미지 추출·
triage·참고자료 필터는 모델과 무관하게 동일하며, 사전 감사로 유실 0을 확인했다
(`docs/audit/M2-1_시각리콜_기준선_20260706.md`).

## 2. 어떻게 측정했나

### 2.1 통제 설계 (이 벤치마크의 핵심)

파이프라인은 텍스트 추출과 vision 판독을 별개 스테이지로 돌린다. 우리는:

- **텍스트 스테이지 고정**: 백엔드 gemini-2.5-flash-lite + LLM 응답 캐시
  (`.cache/llm_responses_gemini_v5`) 공유 → 모든 후보 실행에서 텍스트 호출은
  캐시 히트(신규 호출 ~0, 비용 ~0). 후보 간 차이가 텍스트 품질에서 나올 수 없다.
- **vision 스테이지만 교체**: 환경변수 `STAGE_PROVIDER_VISION`/`STAGE_MODEL_VISION`
  (v5의 단계별 오버라이드 인프라) — 코드 수정 0.
- 동일 입력(서울 PDF), 동일 정답지, 동일 채점기.

### 2.2 후보와 실행 설정

| 후보 | 실제 모델·설정 | 호출 방식 |
|---|---|---|
| flashlite | gemini-2.5-flash-lite (파이프라인 기본값) | Gemini API |
| flash | gemini-2.5-flash | Gemini API |
| pro | gemini-2.5-pro | Gemini API |
| claude | Claude CLI 기본 모델 (`claude -p`, 이미지 파일 전달) | 로컬 CLI (구독 quota) |
| codex | **gpt-5.5, reasoning xhigh** (`codex exec`, `~/.codex/config.toml` 기본값) | 로컬 CLI (구독 quota) |
| openai | (미측정 — OPENAI_API_KEY 부재) | — |

주의: CLI 후보의 성적은 "그 CLI의 그날 기본 설정"의 성적이다. 재현 시 위 설정을
맞추거나 결과 문서에 자신의 설정을 명기할 것.

### 2.3 재현 절차 (그대로 복사해 실행)

```bash
# 0) 전제: GEMINI_API_KEY(.env), 텍스트 캐시(.cache/llm_responses_gemini_v5),
#    정답지(data/golden/서울_시각요소_인벤토리_v1.xlsx) — 전부 레포에 있음(캐시 제외).
#    캐시가 없으면 서울 풀런 1회로 생성: python main.py 서울특별시_탄소중립계획.pdf -o output/서울_기본.xlsx

# 1) 안전 스모크 (API 비용 0 — 캐시 미스가 나면 즉시 실패하도록 기본 설정됨)
python scripts/benchmark_vision.py 서울특별시_탄소중립계획.pdf \
    --candidates flashlite --output-dir output/vision_bench_스모크

# 2) 실측 (캐시 미스 = 실제 과금 호출을 명시적으로 허용해야만 실행됨)
python scripts/benchmark_vision.py 서울특별시_탄소중립계획.pdf \
    --candidates flash,pro,codex --allow-cache-miss --output-dir output/vision_bench

# 3) 결과: {output-dir}/M2-3_vision벤치마크_*.md(비교표) + 표본채점지.md(값 대조용)
#    후보별 원자료: {output-dir}/{후보}/audit/*.json (리콜·유실), pipeline.log
```

비용·시간 가이드(서울 1문서, vision ~260이미지 배치 기준 실측): gemini 계열 후보당
$1~5·20~35분, CLI 후보는 과금 대신 구독 quota를 소모하며 40~70분. **CLI 후보는
quota 한도에 걸리면 결과가 무효가 되므로**(아래 4.3) 한도 여유를 확인하고 돌릴 것.

## 3. 결과

| 후보 | 리콜 (82요소) | vision_유실 | 실행 시간 | 판정 |
|---|---:|---:|---:|---|
| **gemini 2.5 pro** | **0.976** | **2** | **1,282초** | 유효 — **1위** |
| codex (gpt-5.5 xhigh) | 0.951 | 4 | 2,869초 | 유효 — 2위 |
| gemini flash-lite (현 기본) | 0.707 | 24 | (캐시 재현) | 유효 |
| gemini flash | 0.695 | 25 | 2,087초 | 유효 |
| claude CLI | (0.012) | (81) | 3,775초 | **무효** — quota 한도 74회 감지, 능력이 아닌 한도를 측정함 |
| openai | 미측정 | — | — | 키 부재 |

- 유형별(1·2위): pro 그래프 0.987·도식 0.8 / codex 그래프 0.961·도식 0.8.
- codex 참고: 비통제 조건(텍스트도 codex인 풀런)에서는 0.988이었다. 통제 조건
  (텍스트=gemini 고정)에서 0.951로 내려온 차이는 실행 간 변동 또는 텍스트-vision
  상호작용의 존재를 시사한다 — 단정하지 않고 기록만 남긴다.
- **결정 권고**: vision 스테이지 기본값을 `gemini-2.5-pro`로 — 1위 성능, 최단 실행
  시간, quota 의존 없음(API 과금), 남은 유실 2건. 채택은 별도 커밋으로(원칙: 측정
  근거 + 사람 승인).

## 4. 발견 (결과보다 오래 남을 것들)

### 4.1 모델 등급이 프로바이더보다 컸다

flash-lite(0.707)→flash(0.695)는 차이가 없고, flash→pro는 +0.28이다. 처음에
flash 결과만 보고 "gemini 프로바이더가 이 태스크에 약하다"는 가설을 세웠지만
pro가 기각했다 — **같은 프로바이더 안에서 등급이 갈랐다**. 시사점: VLM 선택에서
"어느 회사"보다 "어느 등급"이 먼저다.

### 4.2 실패는 한 단계에 몰린다

모든 후보에서 이미지 추출·triage·필터 유실은 0 — 격차는 전부 vision_유실에서
났다. 벤치마크를 깔때기 단계로 분해하지 않았다면 "파이프라인이 나쁘다"와 "모델이
나쁘다"를 구분할 수 없었을 것이다.

### 4.3 인프라 잡음이 측정을 오염시킨다 (그리고 방어법)

- claude 후보는 quota 한도로 붕괴(0.012) — 로그의 한도 감지 74회가 증거다. 겉보기
  숫자만 보면 "claude가 못 읽는다"로 오독된다. **CLI/구독 기반 후보는 한도 상태가
  측정의 일부**이므로, 무효 판정 기준(로그의 quota 마커)을 정의해 둬야 한다.
- gemini는 측정 전날 503 폭풍으로 보충런 5회가 필요했다. 캐시 공유 설계 덕에
  재실행 비용이 수렴했다(성공분 재사용, 실패분만 재호출).

### 4.4 정답지의 품질이 측정의 절반이다

자동 생성 정답지(v1)로는 리콜이 0.827로 보였지만, 사람 교정 3라운드 후 같은
파이프라인이 0.988(codex 풀런 기준)로 판명됐다 — 오차의 대부분이 정답지 쪽에
있었다. 특히 "렌더 이미지만 보고 텍스트표/이미지표를 구분할 수 없다"는 계통
오류는 AI 단독 정답지 제작의 한계로, 사람 검증 단계를 생략하면 벤치마크 자체가
왜곡된다.

## 5. 한계

1. **단일 문서**(서울) — 지자체별 서식 다양성이 반영되지 않음. M3(강원·경기)에서 확장.
2. 리콜 중심 — 값 정확도는 표본 15개 대조(3차 지표)까지만 설계됐고 전수 채점은 아님.
3. claude 미측정(quota), openai 미측정(키 부재) — 조건이 갖춰지면 같은 절차로 추가.
4. CLI 후보의 설정 의존성 — 재현자는 자기 CLI 설정을 명기해야 비교 가능.
